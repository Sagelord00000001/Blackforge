# Blackforge Reconnaissance Capability Foundation (Phase 5)

Phase 5 gives Blackforge a **typed, deterministic, authorization-gated reconnaissance**
surface. It is the first capability family built on the Phase 4 world model: every recon
run produces evidence and world-model facts that are **derived from actual (mocked, but real
shaped) tool output** — never invented by the LLM.

The subsystem is **stdlib-only** (SQLite + pydantic + time). No model weights, no network
I/O, no external services. All tool output is generated by a deterministic mock tool scoped
to documentation-only test ranges.

---

## 1. Guiding principles

1. **Typed capabilities only.** Six reconnaissance capabilities
   (`recon.host_discovery`, `recon.service_discovery`,
   `recon.technology_identification`, `recon.dns`, `recon.http_metadata`,
   `recon.tls_metadata`). There is **no generic execution surface**: the engine cannot run
   arbitrary commands or unknown capabilities (`ReconExecutionError`).
2. **Authorization before execution.** Every run validates mission scope targets **and**
   capability allow-lists *before* the tool executes. Out-of-scope targets and
   out-of-scope capabilities are denied by `AuthorizationError` with no evidence written.
3. **Fixed pipeline.** capability → mock tool → normalization → evidence
   (artifact + typed observations, `derived_from`) → world model materialization →
   best-effort memory link. A single `ReconResult` returns status, observations, and
   evidence ids.
4. **No invented authority.** Every observation row has a deterministic `dedup_key` and is
   linked `derived_from` an artifact row carrying the raw (mock) tool output. Rerunning a
   capability is **idempotent**: identical evidence ids, unchanged world state.
5. **Honest confidence.** ACTIVE direct observations (host, service, http, tls) default to
   `HIGH`; technology identification is `MEDIUM`; DNS / passive data is `LOW`.
6. **Deterministic mock data.** Hosts map to documentation ranges (`192.0.2.0/24`,
   `198.51.100.0/24`, `203.0.113.0/24`) with stable fallbacks derived from a SHA-256 hash
   of the hostname — no randomness, no real hosts.
7. **Mission isolation.** Evidence and world-model facts are scoped to the mission on every
   query; a second mission's run is fully disjoint.

## 2. Capability surface

| Capability | Mode | Risk | Target types | Produces |
|---|---|---|---|---|
| `recon.host_discovery` | active | low | domain, ip, cidr | host |
| `recon.service_discovery` | active | medium | domain, ip | service |
| `recon.technology_identification` | passive | low | domain, ip, url | technology |
| `recon.dns` | passive | low | domain | dns |
| `recon.http_metadata` | active | medium | domain, url | http |
| `recon.tls_metadata` | passive | low | domain, ip | tls |

Each capability registers its own `ReconCapabilityMeta` (version `1.0.0`,
`authorization_required=True`, `world_model=True`) and declares
`evidence_types_produced=["artifact", "observation"]`.

---

## 3. Pipeline

A run goes through `ReconEngine._execute`:

1. **Mode resolution** — request mode (default `active`) can be overridden via `params`.
2. **Target-type check** — the capability's `supported_target_types` must accept the
   resolved target type (`domain` / `ip` / `cidr` / `url`).
3. **Authorization** — target scope + capability allow-list checked (see §1.2).
4. **Tool run** — the deterministic `MockReconTool` method executes with a timeout.
5. **Normalization** — the capability's adapter turns raw (mock) output into typed
   `Observation` models, emitting warnings and discarding malformed rows
   (`ReconNormalizationError`). A partial parse yields status `partial`.
6. **Evidence persistence** — one artifact row (raw data + provenance) plus one
   observation row per normalized observation, each `derived_from` the artifact.
   Dedup keys make reruns idempotent; `max_observations` truncation yields `limited`.
7. **World materialization** — observations become entities/edges:
   host → `ASSET`; service/port → `SERVICE` (`namespace=<host>`) + `ASSET exposes SERVICE`;
   technology → `TECHNOLOGY` (`namespace=<host>`) + `SERVICE uses TECHNOLOGY`;
   http → `ENDPOINT` (URL canonical form) + `SERVICE exposes ENDPOINT`;
   tls → `ENDPOINT` (namespace `tls`), no edges; dns → evidence only + `ASSET` per A/AAAA
   answer; network → `NETWORK` (canonical CIDR), no edges.
8. **Best-effort memory** — resolvable memory links are written; failures are logged, never
   fatal.

The engine type-checks each run; `ReconResult.status` is one of
`success | partial | limited | timeout | failed` and `authorized` records whether the
authorization gate was passed.

---

## 4. Evidence model

- **Artifacts** carry `raw_data` JSON, source capability, normalized target, and the
  `derived_from` root of the chain.
- **Observations** carry `kind`, host/port/… fields, summary, `source_capability`, and
  `dedup_key`.
- Every observation row links `derived_from` its run's artifact. Reruns resolve the
  existing dedup key and reuse the artifact, adding **no** new rows.

See `docs/evidence.md` for the core evidence store.

---

## 5. Mock tool

`MockReconTool` is deliberately boring:

- Known demo hosts (`web.example.com`, `mail.example.com`, `db.example.com`, …) return
  fixed service/port/product/banner data.
- Unknown hosts get a **deterministic** SHA-256-derived placeholder host/IP inside
  `192.0.2.0/24` (documentation range only) with shallow data.
- `PASSIVE` mode additionally reports observation networks (`192.0.2.0/24`) and marks
  passive service state as `inferred`; `ACTIVE` mode never invents networks.
- No sockets, no subprocesses, no network I/O — a runtime grep test asserts the recon
  package never imports `os.system`/`subprocess`/`socket`/`requests`/`http.client` or
  calls `eval`/`exec`/`pickle`.

---

## 6. Bootstrap integration

`app.recon_engine` is constructed during `BlackforgeApp.__init__` (after the world model
resolves) with the shared capability registry, evidence store, world model, memory bridge,
and authorization boundary. `app.verify()` now includes `recon_ready`, which requires the
engine to exist and exactly six capabilities to be registered. The engine registers the six
recon capabilities into the shared registry only if absent — it never clobbers
`register_defaults()` output.

---

## 7. Scope notes

- Reconnaissance is **describing, not exploiting**: the mock tool only ever returns
  metadata. There is no attack-path reasoning, no exploitation, no credential handling.
- Attack-graph-only concepts remain rejected at the world-model enum layer (see
  `docs/world-model.md`) and are **out of scope**.
- Real network tooling (active scanners, credential-based enumeration) is out of scope for
  this phase.
